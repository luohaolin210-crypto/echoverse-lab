# 游戏项目工作流

## 阶段 A：项目简报

先填写 `templates/game-brief.md`。如果平台、玩家、核心动作或成功条件尚未确定，不进入大规模实现。

产出：一页项目简报、风险清单、最小垂直切片范围。

## 阶段 B：垂直切片

只做一条完整路径：

1. 进入游戏。
2. 看懂目标。
3. 执行核心动作。
4. 获得即时反馈。
5. 遇到一次变化或选择。
6. 得到成功、失败或阶段性结果。
7. 能重新开始或继续。

产出：可运行构建、三张关键截图、一次完整试玩记录。

## 阶段 C：视觉与游戏感

使用 `templates/visual-spec.md` 固定视觉语言，并优先处理玩家最常看到的画面：

- 游戏开始后的第一屏。
- 核心动作发生的位置。
- 成功或失败反馈。
- 关键 UI 与状态面板。

视觉改进必须与玩法状态绑定；例如受伤不只是变红，还应有短暂的动作、音效、镜头或粒子反馈。

产出：前后对比截图、资产清单、关键反馈清单。

## 阶段 D：内容扩展

先找出核心循环中最容易重复的部分，再增加变化：

- 空间变化：路线、遮挡、距离、视线。
- 敌我变化：行为、组合、节奏。
- 规则变化：限制、资源、风险回报。
- 信息变化：线索、叙事、解锁。
- 奖励变化：能力、外观、选择。

每新增一类内容，至少说明它改变了哪个玩家决策。

## 阶段 E：回归与交付

每轮改动都执行最小检查：

- 能否启动并进入目标场景。
- 核心输入是否仍然有效。
- 成功和失败条件是否仍然可达。
- UI 是否仍然可读。
- 是否出现明显卡顿、报错或资源缺失。
- 重新开始是否恢复干净状态。

产出：试玩报告、已知问题、下一轮优先级。

## 优先级规则

优先修复：

1. 阻止玩家理解或继续游戏的问题。
2. 核心动作没有反馈或结果不可信的问题。
3. 第一屏和关键路径的视觉问题。
4. 会阻塞后续内容的架构问题。
5. 只影响边角内容的美化问题。
